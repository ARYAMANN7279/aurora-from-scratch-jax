# Stage 4 Report: Perceiver level aggregator and decoder

Spec: `handouts/stage04_perceiver.md`. Code: `src/aurora/{attention,perceiver}.py`.
Tests: `tests/test_stage4_gates.py`. Numbers are copied from `results/gates.txt`.

## Verdict

**Stage 4 acceptance NOT met.** The acceptance test needs S1 and S4 to hit; both miss. Through
L = 3 latent levels, the one shared model reconstructs the evaluation frames to a relative L2
error of **0.167** (C = 3, 16²), **0.085** (C = 5, 64²), **0.063** (C = 6, 128²) and **0.060**
(C = 8, 512²), against bars of 0.02–0.05. The implementation is correct (all 8 gates pass). The
misses look like under-training rather than a capacity limit, but that is not measured: every
error of the shared model was still falling at step 6000 (16²: 0.187 → 0.167 over the last 1000
steps), each resolution gets only 1500 of the 6000 steps, and a model trained on one resolution
for all 6000 steps reaches 0.040–0.049 at every C (S5).

Predictions: S5 HIT; S1–S4 and S6 MISS. S5 and S6 turned out to be confounded with the training
budget (amendment A1 in the spec); their original verdicts are kept.

**Follow-ups (pre-registered 30 Sep 2026; the verdicts above stand).** F1 trained the 16² control
(C = 3) for 48,000 steps and reached **0.016**, below S1's bar of 0.02: the bar is within reach of
this autoencoder given more training (F1-P1 HIT, F1-P2 MISS). F2, the shared model at a matched
per-resolution budget, is running on the lab machine's CPU. See "Follow-ups" below.

**What S5 and S6 do and do not show.**
* Each control is a separate run on one resolution for all 6000 steps, so it differs from the
  shared model in two ways at once: no compression (L = C) and 4× the per-resolution training
  budget. S5 therefore does not isolate compression. At C = 3 there is nothing to decompress
  (L = C = 3), and that control still cuts the error from 0.167 to 0.043: the budget and sharing
  effect is at least as large as any compression effect.
* The S6 ablation is also a dedicated 64² run, so comparing it with S2 (from the shared run)
  mixes the ablation with the budget. The closest matched pair is the 64² control (level
  encodings on, L = 5) against the ablation (encodings off, L = 3): 0.041 vs 0.049, with curves that
  coincide to step 3000 (0.114 / 0.081 / 0.068 vs 0.114 / 0.082 / 0.067). Exploratory reading:
  at C = 5 the aggregator tells the bands apart without level encodings, plausibly because the
  bands differ strongly in content (scale and spectrum). A matched run (L = 3, 64² only, encodings
  on) would settle it.

## Follow-ups (pre-registered 30 Sep 2026)

Predictions in the spec (§5, F1 and F2), committed before any run. Scored by
`score_followups.py` → `results/followups_analysis.json`.

**F1: can the 16² autoencoder reach S1's bar at all?** The C = 3 control (L = C = 3, so no
compression) was trained 8× longer: 48,000 steps at the same constant learning rate. The spec's
mention of a stretched cosine schedule was wrong; see the F1 note in §5. One run (key 0), as for
S1–S6. Result: `results/f1_nocompress_16_48k.json`.

| # | Prediction | Measured | Verdict |
|---|---|---|---|
| F1-P1 | error < 0.029 (a third below the 6000-step control's 0.043) | 0.0160 | **HIT** |
| F1-P2 | S1's bar still not reached: error > 0.02 | 0.0160 | **MISS** |

| step | 6000 | 12,000 | 24,000 | 36,000 | 48,000 |
|---|---|---|---|---|---|
| error, 16² | 0.0430 | 0.0323 | 0.0212 | 0.0207 | 0.0160 |

* **S1's bar is within reach at 16².** The error first dips below 0.02 at step 22,000, and every
  one of the 24 checks after step 36,000 is below it (0.012–0.020). The S1 miss is therefore not a
  limit of this autoencoder at C = 3. Whether the shared model, which also serves the other
  resolutions, gets there is F2's question.
* **A single end-point is a noisy reading.** At a constant learning rate the evaluation error moves
  between 0.012 and 0.020 over the last 12,000 steps. The S1–S6 numbers are single end-points at a
  constant rate too.
* The first 6000 steps repeat the original control: 0.0430154 at step 6000 on the lab machine's
  CPU, against 0.0430152 on its GPU.
* Ran on one CPU core of the lab machine (single-threaded XLA): 8.0 ms per step, 6.8 min in all.

**F2: the shared model at a matched per-resolution budget** (24,000 steps, the controls' 6000 per
resolution). Running on 4 cores of the lab machine's CPU since 1 Oct 03:02 (6.9 s per 512² step,
about 13 h). Its first attempt, on an idle GPU card, took the card from below 85 °C to 92 °C within
21 s and was stopped (F2 note in §5 of the spec). At step 500 the CPU run matches the original GPU
run's errors to 1.8e-6 at every resolution, so its first 6000 steps replay the S1–S4 run.

## GPU runs: environment, data and commands

* Lab VM, NVIDIA RTX PRO 6000 Blackwell; JAX 0.10.2 with CUDA 12; float32 with matmul precision
  `highest` (TF32 off), the same setting as every E-run.
* Data: `acc_v1` re300_kf4 seeds 0–6 were regenerated on the VM's CPU (Xeon w3-2525, single-threaded
  XLA). They are statistically, not bitwise, identical to the copy used for Stages 7–10 (see the
  Stage 2 report). The 512² frames came from `make_512.py` on the GPU.
* Median time per step (shared model): 7.2 / 8.0 / 14.0 / 236 ms at 16² / 64² / 128² / 512²; the
  512² control (L = 8) takes 402 ms. The shared run's wall time (3.2 h) includes about 2 h in which
  it was paused; the medians exclude the pause.
* **Card placement (corrected 29 Sep 2026).** A launcher bug sent these runs to card 0: the lab
  account's `~/.bashrc` exports `CUDA_VISIBLE_DEVICES=0`, which overrode the card chosen for each
  job. They therefore shared card 0 with our other jobs and, at times, with other users' jobs. The
  thermal guard was watching the claimed card, so pauses and wall times do not reflect the job's
  own card. The numerics are unaffected (identical cards and code). Fixed and verified on 29 Sep;
  see `project_memory.md`.
