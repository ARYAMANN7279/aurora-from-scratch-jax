# Stage 4 Report: Perceiver level aggregator and decoder

Spec: `handouts/stage04_perceiver.md`. Code: `src/aurora/{attention,perceiver}.py`.
Tests: `tests/test_stage4_gates.py`. Numbers are copied from `results/gates.txt`.

## Verdict

**Stage 4 acceptance NOT met.** The acceptance test needs S1 and S4 to hit; both miss. Through
L = 3 latent levels, the one shared model reconstructs the evaluation frames to a relative L2
error of **0.167** (C = 3, 16²), **0.085** (C = 5, 64²), **0.063** (C = 6, 128²) and **0.060**
(C = 8, 512²), against bars of 0.02–0.05. The implementation is correct (all 8 gates pass). The
misses look like under-training rather than a capacity limit, but that is not measured: every
error of the shared model was still falling at step 6000 (16²: 0.187 → 0.167 over the last 1000
steps), each resolution gets only 1500 of the 6000 steps, and a model trained on one resolution
for all 6000 steps reaches 0.040–0.049 at every C (S5).

Predictions: S5 HIT; S1–S4 and S6 MISS. S5 and S6 turned out to be confounded with the training
budget (amendment A1 in the spec); their original verdicts are kept.

**Follow-ups (pre-registered 30 Sep 2026; the verdicts above stand).** F1 trained the 16² control
(C = 3) for 48,000 steps and reached **0.016**, below S1's bar of 0.02: the bar is within reach of
this autoencoder given more training (F1-P1 HIT, F1-P2 MISS). F2 trained the shared model for
24,000 steps, the controls' 6000 per resolution. It reached **0.058 / 0.026 / 0.018 / 0.021** at
16² / 64² / 128² / 512². That beats the single-resolution controls at 64² and above (0.42–0.64×
their error) but not at 16² (1.35×, against a 1.3× bar). So F2-P1 MISSES, on 16² alone; S4's bar is
met (F2-P2 HIT). See "Follow-ups" below.

**Follow-up F3 (pre-registered 3 Oct 2026): 3 of 4 HIT.** The shared model was trained for 192,000
steps, 32× the registered budget, with two keys on Kaggle T4s.
* **16² reaches S1's bar, but does not hold it.** The 16² window first falls below 0.02 at step
  136,000 (run 0) and 151,500 (run 1). The best single evaluations are 0.013.
* **The constant learning rate throws spikes.** One spike, at step 188,000, puts run 0's final
  window back at 0.038 (F3-P1 MISS; run 1 ends at 0.017).
* **The other bars are met.** 64² meets S2's bar (F3-P2 HIT), and 128² and 512² keep theirs (F3-P3
  HIT).
* **16× is not enough at 16²:** 0.026 at 96,000 steps in both runs (F3-P4 HIT).
* **The registered verdict stands.** Stage 4 is not met at its registered budget, and at 32× the
  budget S1 is reached only intermittently.

**Follow-up F4 (pre-registered 3 Oct 2026): 4 of 4 HIT. With a decaying learning rate, every bar is
met and held.** F3 was rerun exactly, except that the rate decays on a cosine schedule from 3e-4 to
3e-6 over the 192,000 steps.
* **Final windows,** 16² / 64² / 128² / 512²: **0.0078 / 0.0022 / 0.0012 / 0.0011** (key 0) and
  **0.0085 / 0.0026 / 0.0013 / 0.0012** (key 1), against bars of 0.02 / 0.02 / 0.03 / 0.05.
* **16² holds the bar.** It goes below S1's bar at step 89,000 (key 0) or 96,500 (key 1) and stays
  there.
* **Stage 4's acceptance test, S1 and S4, is met at 32× the registered budget with this schedule.**
  The verdict at the registered 6000 steps stands.

## Changes after the spec
* The MLP inside the Perceiver block uses the **exact (erf) GELU**, as Aurora does; the first
  version used the tanh approximation. The spec says only "GELU". All gates were rerun and pass.
* The 512² frames for S4 are generated by `make_512.py` on the GPU box. A CPU run was started,
  then stopped to free a core for Stages 6–8.

**What S5 and S6 do and do not show.**
* Each control is a separate run on one resolution for all 6000 steps, so it differs from the
  shared model in two ways at once: no compression (L = C) and 4× the per-resolution training
  budget. S5 therefore does not isolate compression. At C = 3 there is nothing to decompress
  (L = C = 3), and that control still cuts the error from 0.167 to 0.043: the budget and sharing
  effect is at least as large as any compression effect.
* The S6 ablation is also a dedicated 64² run, so comparing it with S2 (from the shared run)
  mixes the ablation with the budget. The closest matched pair is the 64² control (level
  encodings on, L = 5) against the ablation (encodings off, L = 3): 0.041 vs 0.049, with curves that
  coincide to step 3000 (0.114 / 0.081 / 0.068 vs 0.114 / 0.082 / 0.067). Exploratory reading:
  at C = 5 the aggregator tells the bands apart without level encodings, plausibly because the
  bands differ strongly in content (scale and spectrum). A matched run (L = 3, 64² only, encodings
  on) would settle it.

## Follow-ups (pre-registered 30 Sep 2026)

Predictions in the spec (§5, F1 and F2), committed before any run. Scored by
`score_followups.py` → `results/followups_analysis.json`.

**F1: can the 16² autoencoder reach S1's bar at all?** The C = 3 control (L = C = 3, so no
compression) was trained 8× longer: 48,000 steps at the same constant learning rate. The spec's
mention of a stretched cosine schedule was wrong; see the F1 note in §5. One run (key 0), as for
S1–S6. Result: `results/f1_nocompress_16_48k.json`.

| # | Prediction | Measured | Verdict |
|---|---|---|---|
| F1-P1 | error < 0.029 (a third below the 6000-step control's 0.043) | 0.0160 | **HIT** |
| F1-P2 | S1's bar still not reached: error > 0.02 | 0.0160 | **MISS** |

| step | 6000 | 12,000 | 24,000 | 36,000 | 48,000 |
|---|---|---|---|---|---|
| error, 16² | 0.0430 | 0.0323 | 0.0212 | 0.0207 | 0.0160 |

* **S1's bar is within reach at 16².** The error first dips below 0.02 at step 22,000, and every
  one of the 24 checks after step 36,000 is below it (0.012–0.020). The S1 miss is therefore not a
  limit of this autoencoder at C = 3. Whether the shared model, which also serves the other
  resolutions, gets there is F2's question.
* **A single end-point is a noisy reading.** At a constant learning rate the evaluation error moves
  between 0.012 and 0.020 over the last 12,000 steps. The S1–S6 numbers are single end-points at a
  constant rate too.
* The first 6000 steps repeat the original control: 0.0430154 at step 6000 on the lab machine's
  CPU, against 0.0430152 on its GPU.
* Ran on one CPU core of the lab machine (single-threaded XLA): 8.0 ms per step, 6.8 min in all.

**F2: the shared model at a matched per-resolution budget.** The S1–S4 run was trained 4× longer:
24,000 steps, so each resolution gets the controls' 6000 on average. The learning rate is the same
constant rate, and there is one run (key 0).
* **Where it ran:** on 4 cores of the lab machine's CPU, from 1 Oct 03:02 to 15:50 (12.8 h; 6.4 s per
  512² step). Its first attempt, on an idle GPU card, took the card from below 85 °C to 92 °C

| F2-P2 | S4's bar met: error at 512² < 0.05 | 0.0208 | **HIT** |

| | 16² (C = 3) | 64² (C = 5) | 128² (C = 6) | 512² (C = 8) |
|---|---|---|---|---|
| S1–S4 run, step 6000 | 0.167 | 0.085 | 0.063 | 0.060 |
| F2, step 6000 | 0.167 | 0.087 | 0.065 | 0.066 |

| F2 / control | 1.35 | 0.64 | 0.44 | 0.42 |

* **At the same steps per resolution, sharing wins everywhere except 16².** The one shared model
  beats a dedicated model by 1.6–2.4× at 64² and above, and loses by 1.35× at 16². Every step
  updates the same weights, whatever its resolution, so each resolution also learns from the other
  three's steps. Why 16², the coarsest grid, gains least is not measured.
* **The 16² miss is small against the noise.** 1.35 is 4% over the bar, while a single end-point of
  the shared model carries roughly ±10–25% noise (below; 512² alone moves from 0.0237 to 0.0208 over
  the last 500 steps). The verdict is MISS as registered.
* **Still improving.** Every error was still falling at step 24,000. At 16² it went from 0.064 to
  0.058, and at 512² from 0.028 to 0.021, over the last 2500 steps.
* **Against the Stage 4 bars.** This is a reading, not a verdict: S1–S4 stand as scored at 6000
  steps. With 4× the training, the shared model would meet S3 (< 0.03) and S4 (< 0.05). It comes
  close to S2 (0.026 against < 0.02) and stays far from S1 (0.058 against < 0.02). The dedicated 16²
  model reaches S1 with 8× the steps (F1).

**Noise.** F2's first 6000 steps rerun the S1–S4 run on another device, and they show how noisy a
single run of the shared model is:
* The two runs agree to 2e-6 at step 500, but the last-bit differences grow fast (1e-4 at step 1000,
  2e-3 at 1500). From step 3000 on, the runs are effectively independent: at the same step they
  differ by up to 5% / 15% / 19% / 27% at 16² / 64² / 128² / 512².
* At step 6000 the CPU run reads 0.167 / 0.087 / 0.065 / 0.066, against S1–S4's 0.167 / 0.085 /
  0.063 / 0.060.
* A single end-point of the shared model therefore carries roughly ±10–25% noise at 512², and less
  at lower resolution. That applies to S1–S4 as well. (F1's single-resolution control did not
  drift: 0.0430154 vs 0.0430152 at step 6000.)

## Follow-up F3: the shared model trained 32× longer (spec §5, F3)

Predictions committed before any F3 training run (commit e51540d). Scored by `score_f3.py` →
`results/f3_analysis.json`, from `results/f3_main_192k_s{0,1}.json`.

**Design.**
* The S1–S4 run trained for 192,000 steps: 32× the registered 6000, so 48,000 per resolution, which
  is F1's budget at 16².
* The learning rate stays constant (3e-4), with an evaluation every 500 steps. So the curve also
  gives 96,000 steps (16×) and every other budget on the way.
* Two runs, keys 0 and 1 (`--seed`; key 0 is the original initialisation and batch order), one per
  T4 card at the same time. Kaggle job `ugp2-s4f3-runs`, version 2, 7.8–7.9 h per run.
* **Measure:** the mean of 10 consecutive evaluations (5000 steps), because single end-points of
  the shared model are noisy (F2's noise note).

| # | Prediction | Run 0 | Run 1 | Verdict |
|---|---|---|---|---|
| F3-P1 | at 192,000 steps, 16² < 0.02 in both runs | 0.0376 | 0.0167 | **MISS** |
| F3-P2 | at 192,000 steps, 64² < 0.02 in both runs | 0.0200 (0.01996) | 0.0074 | **HIT** |
| F3-P3 | at 192,000, 128² < 0.03 and 512² < 0.05 in both runs | 0.014, 0.015 | 0.005, 0.006 | **HIT** |
| F3-P4 | at 96,000 steps, 16² still ≥ 0.02 in both runs | 0.0262 | 0.0260 | **HIT** |

Mean of 10 evaluations ending at each step, 16² / 64² / 128² / 512²:

| Steps (× registered) | Run 0 | Run 1 |
|---|---|---|
| 24,000 (4×) | 0.065 / 0.032 / 0.023 / 0.026 | 0.066 / 0.032 / 0.024 / 0.027 |
| 48,000 (8×) | 0.040 / 0.018 / 0.013 / 0.014 | 0.040 / 0.021 / 0.016 / 0.017 |
| 96,000 (16×) | 0.026 / 0.012 / 0.009 / 0.010 | 0.026 / 0.011 / 0.007 / 0.008 |
| 144,000 (24×) | 0.026 / 0.012 / 0.009 / 0.010 | 0.024 / 0.012 / 0.008 / 0.009 |
| 192,000 (32×) | **0.038** / 0.020 / 0.014 / 0.015 | **0.017** / 0.007 / 0.005 / 0.006 |
| end-point at 192,000 | 0.0235 / 0.0114 / 0.0087 / 0.0098 | 0.0199 / 0.0119 / 0.0092 / 0.0095 |

**Readings.**
* **S1's bar is within reach of the shared model, but not stable at a constant learning rate.**
  * The 16² window first falls below 0.02 at step 136,000 (run 0) and 151,500 (run 1).
  * The best single evaluations are 0.0136 and 0.0133.
  * After the first crossing, the window is below the bar 43% (run 0) and 72% (run 1) of the time.
  * Run 1 ends at 0.0167, 1.04× F1's dedicated 16² model at the same 48,000 steps per resolution
    (0.0160). At this budget, sharing no longer costs the 16² model much.
* **Spikes decide the end-point.**
  * Both runs show sudden error spikes that hit several resolutions at once (8 and 13 events in which
    at least three resolutions more than doubled), each followed by recovery over a few thousand
    steps.
  * Run 0's spike at step 188,000 (0.188 at 16², 0.127 at 64², 0.096 at 512²) sits inside the
    scored window. Without that one evaluation, the window's mean is 0.0209 at 16² and 0.0081 at
    64².
  * A decaying learning rate would be the obvious remedy. It is not tested here, and it would change
    the registered recipe.
* **The 96k–144k plateau.** Between 96,000 and 144,000 steps the 16² window barely moves
  (0.026 → 0.024–0.026), then falls again. Single end-points at any one budget can mislead, as F2's
  noise note warned.
* **Reproducible across devices at 24,000 steps.** The F3 windows at 24,000 steps (0.065–0.066 at
  16²) match F2's CPU run (0.065) within 2%, so the T4 runs continue F2's curve.
* **Cost:** 0.52–0.53 s per 512² step on a T4 (2.2× the lab card's 0.24 s). The 512² steps take 92%
  of the training time.

## Follow-up F4: F3 with a decaying learning rate (spec §5, F4)

Predictions committed before any F4 run (commit 8eeea5c). Scored by `score_f4.py` →
`results/f4_analysis.json`, from `results/f4_main_192k_cos_s{0,1}.json`.

**Design.**
* F3 exactly: the shared model, 192,000 steps, keys 0 and 1, one per T4 card at the same time, the
  same software, data and evaluation.
* Only the learning rate changes: a cosine decay from 3e-4 to 3e-6 (`--schedule cosine`).
* Kaggle job `ugp2-s4f4-runs`, 8.0–8.1 h per run.
* **Measure:** the mean of the 10 evaluations ending at 192,000 steps, as in F3.

| # | Prediction | Key 0 | Key 1 | Verdict |
|---|---|---|---|---|
| F4-P1 | at 192,000 steps, 16² < 0.02 in both runs | 0.0078 | 0.0085 | **HIT** |
| F4-P2 | at 192,000, 64² < 0.02, 128² < 0.03 and 512² < 0.05 in both runs | 0.0022, 0.0012, 0.0011 | 0.0026, 0.0013, 0.0012 | **HIT** |
| F4-P3 | at 192,000, 16² below F3's for the same key (0.0376, 0.0167) | 0.0078 | 0.0085 | **HIT** |
| F4-P4 | no evaluation after step 144,000 more than twice the median of the 10 before it | none | none | **HIT** |

Mean of 10 evaluations ending at each step, 16² (F3, the constant rate, in brackets) / 64² / 128² / 512²:

| Steps | Key 0 | Key 1 |
|---|---|---|
| 24,000 | 0.066 (0.065) / 0.031 / 0.022 / 0.024 | 0.066 (0.066) / 0.030 / 0.022 / 0.024 |
| 48,000 | 0.037 (0.040) / 0.016 / 0.011 / 0.013 | 0.038 (0.040) / 0.017 / 0.012 / 0.014 |
| 96,000 | 0.018 (0.026) / 0.008 / 0.006 / 0.006 | 0.020 (0.026) / 0.008 / 0.006 / 0.006 |

**Readings.**
* **The constant rate was the limit, not the model.**
  * At the same 192,000 steps, the decaying rate leaves the 16² error 2.0–4.8× lower than F3's
    constant rate, and the other resolutions 3–14× lower.
  * The 16² window falls below S1's bar at step 89,000 (key 0) and 96,500 (key 1), and stays below
    it for the rest of training.
  * F3, at the constant rate, crossed later (136,000 and 151,500) and kept bouncing back.
* **The spikes stop as the rate falls.**
  * F4 still shows sudden spikes while the rate is high: 11 steps with one for key 0, the last at
    124,000 (rate 8.6e-5); 3 for key 1, the last at 69,500.
  * After step 144,000 (rate below 4.7e-5) there are none at any resolution.
* **The shared model now beats the dedicated ones.**
  * At 16² it ends at 0.008, half the error of F1's dedicated 16² model (0.016; 48,000 steps at the
    constant rate).
  * At 64² and above it is 16–45× below the 6000-step single-resolution controls (S5).
  * F1 had no schedule either, so how a dedicated model would do with one is not measured.
* **The schedule helps early too.** At 96,000 steps, with the rate at half its start, the 16² window
  is already 0.018–0.020, against F3's 0.026. The first 48,000 steps are nearly identical to F3's
  (0.037–0.038 against 0.040), as expected while the rate is still above 85% of its start.
* **Stage 4's acceptance test (S1 and S4) is met** with 32× the registered steps and a decaying
  rate. The verdict at the registered 6000 steps stays "not met", as registered.

## GPU runs: environment, data and commands

* Lab VM, NVIDIA RTX PRO 6000 Blackwell; JAX 0.10.2 with CUDA 12; float32 with matmul precision
  `highest` (TF32 off), the same setting as every E-run.

  account's `~/.bashrc` exports `CUDA_VISIBLE_DEVICES=0`, which overrode the card chosen for each
